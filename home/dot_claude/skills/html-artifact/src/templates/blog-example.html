The Cost of Invisible Decisions

Engineering · Jun 28, 2026 · 7 min read
R
Robson Scheffer
Head of Engineering · Retirement Team

Every system carries the weight of decisions nobody remembers making. A timeout set to 30 seconds because someone guessed. A column named type2 because someone didn't want to migrate the original. A cache TTL of zero because a bug was urgent and the fix never came. These aren't bugs. They're invisible architecture.

How invisible decisions form

Invisible decisions don't arrive announced. They come in through the side door: a hotfix at 11pm, a deadline that moved, a PR reviewer who didn't ask why. The code ships. The context evaporates. Six months later, someone is reading a number with no unit and no comment and making their best guess about what it means.

The damage compounds. One invisible decision creates the conditions for the next. The timeout gets cargo-culted into every new service. The column name gets referenced in fifteen places before anyone notices. The cache TTL spawns a whole class of silent failures that look like network problems.

◆
Before every hotfix: write one sentence in the commit message explaining why the number you picked is the right number. Future you will read it at 2am and be grateful.

The audit nobody wants to run

There's a simple test for invisible decisions: ask "why is this the value?" about every magic constant in a file. If the answer is "I don't know" or "it's always been that way," you've found one. The goal isn't to change every value — most of them are probably fine. The goal is to surface which ones you're trusting blindly.

A useful format: timeout_ms = 30_000 # upstream p99 is 22s per INC-4812. Eleven extra characters. The constant is now load-bearing in a way you can reason about. The incident ticket is the diff you can't read in the code — link it.

△
Don't document everything. A comment on every line is noise, not signal. Reserve them for the decisions that would look wrong to a competent reader at first glance. That's the bar.

When it finally matters

Invisible decisions surface at the worst times: incidents, migrations, onboarding. The on-call engineer at 2am doesn't need a mystery — they need to know whether changing this value will fix the problem or make it worse. The person writing the migration script needs to know if type2 means anything or if it's safe to drop. The new engineer needs to know which parts of the codebase are deliberate and which are accidental.

The cost isn't the time to write the comment. The cost is the accumulated uncertainty tax — every decision made under fog instead of clarity, every incident that ran two hours longer than it needed to.

i
This is distinct from over-documentation. The goal is decisions that are traceable, not decisions that are explained. A ticket link beats three paragraphs of rationale.

A practice, not a rule

You won't fix invisible decisions with a style guide. You fix them one PR at a time, when you happen to be reading the code anyway. The habit is: when you stop to read a value and think "huh, why is this here?" — write down the answer before you move on. Leave it better than you found it. Not perfect. Just not invisible.

Good code is code you can reason about. A decision you can trace is a decision you can change safely.
The invisible decisions aren't the ones that were made carelessly. They're the ones made carefully, under pressure, and never written down. — Field note, 2024 incident retrospective
